# PlaywrighteCommerceAppAI

End-to-end test automation framework for an e-commerce application, built with **Playwright + TypeScript**.
It covers two layers:

| Layer | Application under test | Tests |
|---|---|---|
| **Web (UI)** | OpenCart storefront — [awesomeqa.com/ui](https://awesomeqa.com/ui/) or a local OpenCart install | 13 |
| **API** | [FakeStore REST API](https://fakestoreapi.com) — auth, products, users, carts | 36 |

The tests were generated by an AI coding agent from prompt files in [`prompts/`](prompts/), following the
framework conventions in [`playwright-mcp-context.md`](playwright-mcp-context.md).

---

## Tech stack

- **Runner:** `@playwright/test` (Chromium project)
- **Language:** TypeScript (path aliases `@pages/*`, `@utils/*`, `@fixtures/*`, `@api/*`, `@testdata/*`)
- **UI pattern:** Page Object Model + custom fixtures
- **API validation:** Playwright `request` fixture + JSON schema validation with **AJV**
- **Test data:** Faker (random data), CSV / JSON / Excel readers for data-driven tests
- **Config:** `dotenv` (`.env`)
- **Reporting:** list, HTML, JUnit, Allure, and a custom HTML reporter
- **CI:** GitHub Actions (GitHub-hosted Windows runner, web tests only, weekly schedule)

## How we build tests (process)

1. **Write a prompt file** in `prompts/` describing the scenarios (e.g. `fakestore_api_test_prompts.md`,
   `opencart_web_test_prompts.md`).
2. **Give the AI agent** the prompt plus `playwright-mcp-context.md`. The context file defines the folder layout,
   naming, fixture rules, tagging and the order to build things in.
3. **The agent inspects the project first** and reuses existing routes, schemas, page objects, fixtures and utilities
   instead of duplicating them.
4. **For UI tests**, the agent explores the live app with Playwright CLI or MCP to find stable locators, then builds
   page objects → fixtures → specs.
5. **For API tests**, endpoints come from `api/endpoints/routes.ts`, payloads from `RandomDataUtil`, and response
   contracts from `api/schemas/`.
6. **Run locally**, review results and the Allure report, then push. CI runs the suite on a schedule.

## Setup

Prerequisites: Node.js (LTS), Java (for the Allure CLI).

```bash
npm ci
npx playwright install
cp .env.example .env      # then fill in your values
```

Key `.env` values:

| Variable | Purpose |
|---|---|
| `WEB_APP_URL` | Storefront URL, e.g. `https://awesomeqa.com/ui/` |
| `API_BASE_URL` | `https://fakestoreapi.com` |
| `API_USERNAME` / `API_PASSWORD` | FakeStore login for the auth test |
| `USER_ID`, `PRODUCT_ID`, `CART_ID`, `LIMIT` | IDs and limit used by API tests |
| `START_DATE` / `END_DATE` | Cart date-range filter |
| `PRODUCT_NAME`, `PRODUCT_QUANTITY` | Product used by web cart tests |

`.env` is git-ignored — never commit it.

## Running tests

`playwright.config.ts` has `grep: /@master/`, so a plain `npx playwright test` runs the full `@master` suite.

```bash
npm run test:master        # everything
npm run test:api           # API only
npm run test:web           # UI only
npm run test:sanity
npm run test:regression
npm run test:e2e
npm run test:datadriven
```

Locally the browser runs headed; in CI (`CI` set) it runs headless.

## CI — GitHub Actions

Workflow: [`.github/workflows/playwright.yml`](.github/workflows/playwright.yml)

| Trigger | Suite |
|---|---|
| Push / pull request to `main` | `@e2e` |
| Schedule — every Saturday 12:00 AM EST (`0 5 * * 6` UTC) | `@master` |
| Manual (Actions → 🎭 Playwright Tests → Run workflow) | Choose suite, browser, headed/headless |

Every CI run excludes `@api` tests (`--grep-invert "@api"`), so CI runs the web tests only.

After the tests, the `allure-report` job builds the Allure report and publishes it to GitHub Pages
(`https://farukh43.github.io/PlaywrighteCommerceAppAI/`). The link appears on the run page and in the job summary,
along with the pass/fail counts. Pages shows only the latest run. One-time setup: repo → **Settings → Pages →
Build and deployment → Source: GitHub Actions**.

Steps: checkout → Node setup → `npm ci` → install browsers → create `.env` from `.env.example` →
API reachability check → run tests → upload `playwright-report`, `custom-report` and `allure-results` artifacts.

### Why API tests are skipped in CI

`fakestoreapi.com` sits behind Cloudflare, which answers GitHub-hosted runner IPs with **403** (`Cf-Mitigated: challenge`),
so every API test fails on `windows-latest`. Run API tests locally with `npm run test:api`.

To run them in CI later, use a self-hosted runner:

1. Repo → **Settings → Actions → Runners → New self-hosted runner** → Windows x64.
2. Install it in `C:\actions-runner` — **not** under `C:\Windows\System32`, where Windows redirects 32-bit tools
   and `actions/setup-node` fails to extract Node (`7zr.exe ... failed with exit code 2`).
3. Answer **Y** to run it as a service.
4. In the workflow set `runs-on: [self-hosted, windows]` and remove `--grep-invert "@api"`.

The runner machine must be on at the scheduled time; queued jobs are cancelled after 24 hours.

### Repository secrets

Settings → Secrets and variables → Actions:

| Secret | Value |
|---|---|
| `API_USERNAME` | FakeStore username |
| `API_PASSWORD` | FakeStore password |

Optional repository **variable** `WEB_APP_URL` overrides the default `https://awesomeqa.com/ui/`.

### Debugging a failed run

```bash
gh run list
gh run view <run-id> --log-failed            # failed test output
gh run download <run-id> -D ci-reports       # reports, screenshots, videos, traces
gh run rerun <run-id> --failed --debug       # rerun failures with debug logging
```

Generate Allure from CI results:

```bash
npx allure-commandline generate ci-reports/allure-results -o ci-allure --clean
npx allure-commandline open ci-allure
```
